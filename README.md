# effort-fit

> **실험작(Experimental).** 개인 실험으로 만든 Claude Code 플러그인입니다. Claude Code 2.1.295(Windows)에서만 확인했고, 기반이 되는 플러그인 훅 API는 Claude Code 쪽에서 "early access"로 표시돼 있어 다음 버전에서 동작이 깨질 수 있습니다. 판정 기준은 소수의 시험 턴으로 정한 경험칙이며 검증된 지표가 아닙니다.
>
> *Experimental Claude Code plugin that shows whether the session's model and reasoning effort fit the current work. Tested only on Claude Code 2.1.295 (Windows); it relies on an early-access hooks API and may break on later versions.*

사용자가 처음 고른 모델·effort에서 출발해, 턴이 끝날 때마다 최근 사용 패턴에 지금 조합이 맞는지 판정하고 프롬프트 위 패널과 상태줄에 보여 줍니다. 바꿀 필요가 있으면 한 칸씩이 아니라 그 패턴에 맞는 조합을 바로 추천합니다(예: Haiku·medium에서 실패가 쌓이면 Fable·high). 근거가 부족하면 적합하다고 단정하거나 무리하게 낮추지 않고 "추가 관찰 중"으로 둡니다. **패널은 정보만 보여 줍니다. 모델이나 effort를 바꾸지 않고 바꾸는 명령도 띄우지 않습니다. 바꿀지는 사용자가 정하고 직접 바꿉니다.**

```
감지한 요구 수준 ■■■■ 매우 무거움 · 최근 2턴에 강한 실패 신호 3회
지금 Haiku 5.5·medium (가벼움 수준): 변경 권장 → 매우 무거움 수준
추천 Fable·high · 모델 전환 · 대화 전체 약 57k 토큰을 캐시 없이 다시 처리 (마지막 응답의 입력 토큰으로 추정)
대안 Opus·max · 모델 전환 · 대화 전체 약 57k 토큰을 캐시 없이 다시 처리 (마지막 응답의 입력 토큰으로 추정)
캐시가 깨지는 변경은 compaction 직후에 하면 캐시 없이 다시 처리하는 양이 가장 적습니다. 그래도 그 양이 0이 되지는 않습니다.
```

상태줄은 `Haiku 5.5·medium ▲ Fable·high 권장 (감지 매우 무거움)`, `Opus 5.5·high ● 적합 (감지 보통)`, `Opus 5.5·xhigh ◌ 추가 관찰 중 (감지 가벼움)`처럼 한 줄로 보여 줍니다. 패널과 상태줄의 "감지"는 같은 값, 최근 작업에서 감지한 요구 수준입니다. 패널은 여기에 지금 조합이 맡는 수준과 목표 수준을 따로 보여 줍니다. 패널은 "숨기기"로 가릴 수 있고, 판정 상태나 추천이 바뀌면 다시 나타납니다.

## 판정 상태

| 상태 | 뜻 |
|---|---|
| 적합 | 지금 조합이 맡는 수준(`TIER`)이 감지한 요구 수준과 같습니다. |
| 변경 권장 | 다른 수준이 필요하고, 그 수준을 채우면서 지금과 다른 조합이 있습니다. 근거가 약해 감지 수준까지 가지 않고 한 단계만 옮기면 "(감지 수준은 …이지만 근거가 약해 한 단계만)"을 붙입니다. |
| 추가 관찰 중 | 낮출 수준이 감지됐지만 보류했습니다. 최근 5턴 창의 가벼운 턴이 3개 미만일 때입니다. "적합"이 아닙니다. |
| 지원하지 않는 조합 | 지금 모델·effort가 판정표에 없습니다. effort를 쓰지 않는 모델도 여기에 듭니다. |
| 권장할 조합 없음 | 변경이 필요한데, 목표 수준을 채우면서 지금과 다른 조합이 판정표에 없습니다. 이유를 함께 보여 줍니다. |

## 판정 규칙

결정론적 신호만 씁니다. 요구 수준은 최근 5턴(메인 대화)으로 매깁니다. 처음에는 로컬 Ollama로 프롬프트를 분류해 보조 신호로 썼지만, 관찰된 분류가 거의 전부 light였고 추천에 영향을 주는 heavy는 거의 나오지 않아 2026-10-23에 뺐습니다.

| 요구 수준 | 조건 | 추천 | 대안 |
|---|---|---|---|
| 매우 무거움 | 강한 실패 신호 3회 이상 | Fable·high | Opus·max |
| 무거움 | 강한 실패 신호 1회 이상, 또는 큰 작업 턴 2회 이상 | Opus·xhigh | 없음 |
| 가벼움 | 창 안의 턴이 모두 가벼운 턴이고 3턴 이상 | Haiku·medium | Sonnet·low |
| 보통 | 그 밖 | Sonnet·high | Opus·medium |

- **강한 실패 신호의 단위.** 실패한 도구 결과 1건이 사건 1건입니다. 그 사건이 아래 둘 중 하나면 강한 신호 1회로 셉니다. 둘 다 해당해도 1회입니다.
  - 같은 실패(지문)가 이번 턴이나 직전 2턴 안에 이미 있었음
  - 이번 턴에서 편집 직후 Bash가 실패한 일의 두 번째 이후

  첫 번째 수정 후 실패는 세지 않습니다. 테스트를 고치고 돌려 실패를 확인하는 것은 보통의 개발 흐름이기 때문입니다. 예를 들어 같은 오류를 한 턴에 두 번 내면 1회, 세 번 내면 2회입니다. 수정 후 실패가 1·2·3번이면 0·1·2회입니다. 서로 다른 오류는 세지 않습니다. 강한 신호는 최근 5턴 창 안에서 합산하고, 창을 벗어난 턴의 신호는 빠집니다.
- **가벼운 턴.** 도구를 1개 이상 썼고, 4단계 이하·편집 1회 이하·오류 0인 턴입니다. 도구 종류는 따지지 않습니다.
  - 다른 세션에 메시지를 보내거나 상태를 확인하는 짧은 조율 턴도 가벼운 턴입니다. 처음에는 읽기 전용 도구만 쓴 턴으로 한정했는데, 실제 대화 기록 8,665턴을 재현해 보니 가벼운 턴이 0.7%뿐이었고 하향 추천이 사실상 나오지 않았습니다. 이렇게 바꾸면 가벼운 턴이 41.5%가 되고, 하향 추천은 3.8%의 턴에서 나옵니다. 다만 짧은 조율 턴이 낮은 모델로도 충분한지는 재현으로 확인할 수 없습니다.
  - 도구를 하나도 쓰지 않은 턴은 가볍지도 무겁지도 않은 턴으로 둡니다. 설계·코드 리뷰·논리 분석은 도구 없이도 어렵기 때문입니다.
  - 5단계 이상 걸린 턴은 읽기만 했더라도 가벼운 턴이 아닙니다.
- **큰 작업 턴.** 10단계 이상이거나 편집 3회 이상인 턴입니다. 실제 대화 기록의 단계 수 분포(상위 10% 경계 약 14)를 보고 정했습니다.
- **거절.** 다음 도구 결과는 모델 능력과 무관하므로 도구 수·오류·강한 신호에서 빼고 따로 셉니다(기록의 `refusals`).
  - 권한 규칙·auto mode·훅이 막은 결과
  - 사용자가 거절하거나 중단한 결과

  판별 기준은 Claude Code의 표준 거절 문구, 플러그인 `deny`, 대화 기록의 `toolDenialKind` 셋 중 하나입니다.
- **지금 조합이 맡는 수준(`TIER`)과 추천표(`TARGETS`)는 가정입니다.** 기록으로 보정할 대상이고, 추천표의 모든 조합은 자기 수준에 놓이도록 테스트로 묶어 두었습니다.
  - Opus·high는 "보통" 수준으로 봅니다. 실제 작업 6,758턴(90%가 Opus·high)을 재현했을 때, Opus·high를 무거움으로 두면 69%의 턴에서 낮추라는 추천이 떴습니다.
  - 이것은 추천 빈도에 대한 근거입니다. Sonnet·high 같은 낮은 조합으로 같은 품질을 얻는다는 증거는 아닙니다. 사용자가 평소 고르는 조합을 보통의 기준으로 삼은 판단입니다.
  - Fable을 맨 위에 둔 근거는 [공식 문서](https://code.claude.com/docs/en/model-config)입니다.
- **추천 후보 검증.** 후보마다 세 단계를 거칩니다.
  1. 지금 모델 버전이 지원하는 effort로 바꿉니다. xhigh가 없는 Opus 4.6·Sonnet 4.6에서는 high를 먼저, 그다음 max를 시도합니다.
  2. 지금 조합과 같은 후보는 뺍니다.
  3. `TIER`가 목표 수준에 못 미치는 후보는 뺍니다. 내릴 때는 지금 수준보다 낮은 후보만 남깁니다.

  예를 들어 Opus 4.6·high가 무거움으로 판정되면, Opus·xhigh는 Opus·high(지금 조합이자 보통 수준)가 되어 빠지고 Opus·max를 추천합니다.
- **올림.** 감지 수준으로 바로 올립니다. 다만 두 수준 이상 올리는 것은 강한 신호가 2회 이상일 때만이고, 아니면 한 단계만 올립니다.
- **내림.** 최근 5턴 창의 가벼운 턴이 3개 미만이면 보류하고 "추가 관찰 중"으로 둡니다. 두 수준 이상 내리는 것은 5턴이 모두 가벼운 턴일 때만입니다.
- **실패 판정.** 실패는 도구 결과의 오류 표시로 셉니다. Bash는 오류 표시가 없어도 다음 경우를 실패로 셉니다. 출력 마지막 줄이 0이 아닌 종료 코드 표기(`exit=127`, `Exit code: 2` 등)이거나, bash의 `…: command not found` 줄이 있는 경우입니다. 명령 뒤에 다른 명령을 붙여 실패가 가려지는 경우(`foo; echo "exit=$?"`)를 위한 것입니다.
- **실패의 같음.** 오류 출력의 첫·마지막 의미 있는 줄로 봅니다(Bash의 `Exit code N` 줄은 무시).
- **판정에서 빼는 턴.** 서브에이전트 완료 보고나 백그라운드 작업 알림으로 시작된 턴은 판정에서 뺍니다. 서브에이전트는 대화가 따로라 메인 캐시와 무관하므로 별도 줄로 판정합니다.

## 캐시 영향 표시

[공식 문서](https://code.claude.com/docs/en/prompt-caching)가 보장하는 범위만 표시합니다.

- **모델 전환.** 모델마다 캐시가 따로라, 바꾼 다음 요청은 대화 전체를 캐시 없이 다시 읽습니다.
- **effort 변경.** Opus 5.5·Sonnet 5.5·Haiku 5.5·Fable 5.1을 API 키나 Claude 구독으로 쓰면 캐시가 유지됩니다. 그 밖의 모델과 Amazon Bedrock·Google Cloud Agent Platform 등에서는 캐시가 깨집니다.
- **compaction.** 대화를 짧은 요약으로 바꾸고, 그다음 턴은 그 요약만큼만 대화 캐시를 다시 만듭니다.

이에 따라 추천과 대안마다 다음 중 하나를 붙입니다.
- 캐시가 유지되는 effort 변경: "effort만 변경 · 캐시 유지 (공식 문서 기준)"
- 그 밖의 변경: "대화 전체 약 N k 토큰을 캐시 없이 다시 처리 (마지막 응답의 입력 토큰으로 추정)"
- 토큰 수를 얻지 못했을 때: "양은 알 수 없음"

N은 `$.session.usage().context.tokens`, 즉 마지막 응답의 입력 토큰(캐시 안 된 입력·캐시 쓰기·캐시 읽기의 합)입니다. 정확한 비용이 아니라 다시 처리할 양의 추정치입니다.

캐시가 깨지는 추천이 있으면 compaction 직후 토스트로 "지금 바꾸면 캐시 없이 다시 처리하는 양이 가장 적다"고 알립니다. 손실이 없다는 뜻은 아닙니다. 새 모델에서는 시스템 프롬프트·프로젝트 맥락·요약을 캐시 없이 다시 처리합니다. 또 패널의 토큰 수는 다음 턴이 끝날 때까지 compaction 이전 값입니다.

## 설치

터미널의 Claude Code 프롬프트에서:

```
/plugin install effort-fit --marketplace jesuslim3-prog/effort-fit
```

`Add marketplace?`에 `y`, 그다음 설치 범위를 고릅니다. 데스크톱 앱의 Code 탭에서는 이 명령을 쓸 수 없으니 터미널에서 설치하세요.

개발용으로 폴더에서 바로 띄우려면:

```
claude --plugin-dir <이 저장소를 받은 폴더>
```

## 기록

턴마다 판정 근거를 플러그인 저장소(`~/.claude/plugins/store/` 아래 effort-fit 파일)에 최근 300건까지 남깁니다: `log`(메인 턴), `agentLog`(서브에이전트), `compactLog`(compaction). 턴 항목에는 판정 신호, 감지한 요구 수준(`level`), 지금 조합의 수준(`current`), 목표 수준(`target`), 판정 상태(`status`), 추천 조합(`recommended`), 강한 실패 신호(`strong`), 거절(`refusals`)과 함께 세션 ID, `turnId`, 소요 시간, 그 턴의 토큰 합계(입력·출력·캐시 읽기·캐시 쓰기)가 들어갑니다. 모델이나 effort를 바꾼 직후 턴의 캐시 쓰기 토큰을 보면 그 환경에서 캐시가 실제로 깨졌는지 확인할 수 있고, 다음 턴의 모델·effort를 보면 사용자가 추천을 따랐는지 알 수 있습니다. 판정 기준이 실제 작업에 맞는지 나중에 대조하는 용도입니다. 모델에게는 판정 결과를 보내지 않습니다(프롬프트에 넣지 않음).

## 한계

- "적합"을 직접 재는 방법은 없습니다. 위 신호는 모두 대리 지표입니다.
- 실패 감지는 도구 호출의 오류 표시와, Bash의 경우 위의 출력 흔적 두 가지에 의존합니다. 그 밖의 방식으로 실패가 가려지면(예: `|| true`, 종료 코드를 출력하지 않는 `; echo done`) 잡히지 않고, 출력 마지막 줄에 우연히 `exit=1` 같은 글자가 오면 실패로 잘못 셀 수 있습니다.
- 읽기 전용 여부(Claude Code 자체 판단)는 기록에만 남고 판정에는 쓰지 않습니다.
- 캐시 유지 판단은 모델 이름과 환경 변수(`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`)로 합니다. Claude apps gateway와 HIPAA 구성은 알아낼 수 없어 그 환경에서는 "캐시 유지" 표시가 틀릴 수 있습니다. 그 경우에도 캐시가 살아 있으면 Claude Code가 effort 변경 전에 확인을 묻습니다.
- 거절 판별은 실시간 경로와 재현 경로가 같은 함수를 쓰지만, 근거가 조금 다릅니다. 실시간 플러그인에는 대화 기록의 `toolDenialKind`가 넘어오지 않아 표준 거절 문구로만 판별합니다. 그래서 문구가 다른 거절(예: 보호된 경로 삭제를 막는 `Remove-Item … is blocked`)은 실시간에서는 오류로, 재현에서는 거절로 셀 수 있습니다.
- 테스트는 규칙이 적힌 대로 동작하는지를 확인할 뿐, 추천이 실제로 맞는지를 검증하지 않습니다.
- 최근 5턴 창은 플러그인이 다시 로드되면 비워집니다.

## 개발

```
claude plugin validate .
claude plugin test .
```

판정 로직은 `hooks/judge.ts`, 이벤트 수집과 표시는 `hooks/register.tsx`에 있습니다.

판정 기준을 바꾸기 전에 `tools/replay.mjs`로 기존 Claude Code 대화 기록에 판정을 다시 돌려 보면, 실제 작업에서 패널이 무엇을 보여 줬을지 미리 볼 수 있습니다(Node 23.6 이상, 대화 기록은 읽기만 합니다). 도구 결과는 실시간 플러그인과 같은 집계(`recordTool`)와 판정(`judge`)을 거칩니다.

대화 기록에 없는 정보는 지어내지 않고 표시합니다.
- 읽기 전용 여부: 판정에는 쓰이지 않고 기록용으로만 추정합니다. `readOnlyBasis`에 `estimate:strict`(Bash는 늘 읽기 전용 아님) 또는 `estimate:heur`(명령 첫 단어로 추정)를 적습니다.

그래서 재현 결과는 추천이 얼마나 자주 나오는지에 대한 근거일 뿐, 추천이 맞는지의 근거는 아닙니다.

```
node --no-warnings tools/replay.mjs rows.json ~/.claude/projects/<프로젝트 폴더>
```
